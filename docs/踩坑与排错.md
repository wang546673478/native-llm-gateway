# 踩坑与排错

> 本会话(2026-08)实战踩过的所有坑。每条:现象 → 根因 → 修复 → 预防。
> 修完任何坑后,请把可复用的经验沉淀到这里。

---

## 1. MiniMax 额度错误藏在 HTTP 200 里(不触发 failover)

**现象**:minimax token plan 额度耗尽后,请求仍反复打到 minimax 并失败,不会自动切到 deepseek;用户只能手动改配置。

**根因**:MiniMax 的余额不足(1008)/超套餐(2056)错误是 **HTTP 200 + body `{"base_resp":{"status_code":N}}`**,而两个协议基座只在 `status >= 400` 时解析错误 → 网关把错误体当成功响应透传,ProviderError 从未产生 → failover 不触发、key 不标记。

**修复**:`provider.ParseMiniMaxBaseResp` / `ParseMiniMaxStreamBaseResp`(200 时解析 base_resp;1008/2056 → quota_exceeded → 标记 key + failover)。非 MiniMax 响应无 base_resp 字段,检查为 no-op。

**预防**:新厂商接入时,先实测它的错误格式——**上游错误不一定走 HTTP 状态码**。

## 2. 上游 400 invalid_request 永久禁用 key(整条链被打死)

**现象**:Claude Code 干活后(请求带 tool_use/tool_result 块),deepseek 流中途返回 400 → 之后**连续 502**,且无恢复路径(只能删 key 重建或重启)。

**根因**:`keypool.ReportError` 把 `auth` 和 `invalid_request` 都标 `KeyStatusDisabled`。上游 400 通常是**请求内容问题**(agent 回带其他厂商的 thinking 块、tool 格式差异),不是 key 有问题;永久禁用 key 会把整条链打死。

**修复**:只有 `auth`(401/403-auth)禁用 key;`invalid_request` 只计数。

**预防**:不要用「一次错误」给 key 判死刑;上游 400 ≠ key 坏。

## 3. 白名单语义断层(客户端发假名,key 配真实模型名,403)

**现象**:key 白名单 `['MiniMax-M3','deepseek-v4-flash']`,Claude Code 发 `claude-opus-5` → 403 `model_not_allowed`,尽管路由后明明是 MiniMax-M3。

**根因**:白名单用**客户端原始名**校验,而 catch-all 路由后是真实模型名。

**修复(两次)**:
- 先改为按「路由结果的目标模型」校验(4.5 统一探针)
- 再升级为**白名单参与候选模型选择**:provider 声明过白名单模型就用白名单模型(按白名单顺序);声明里没有的 provider 不参与。现在改白名单 = 改路由目标。

**预防**:任何「名字会被改写」的系统,校验必须发生在**改写之后**;白名单最好直接驱动路由目标而非只做排除。

## 4. 首候选非重试错误 → 客户端收到 200 + 空流

**现象**:Codex 报 `stream disconnected before completion: stream closed before response.completed`,日志里却是 200 ok、几百 ms。

**根因**:`runWithFirstResult` 里首候选非重试错误时 `return` **不写任何响应** → gin 默认 200 + Content-Length 0。流式场景下头部已发,客户端收到空流。

**修复**:非重试错误也走 `handleAllFailed` 正常写错误。

**预防**:failover 循环的所有提前 return 都要问「错误写了吗」。

## 5. Codex 跨厂商切换 400「reasoning_text must be passed back」

**现象**:Codex 从 MiniMax(有推理)切到 deepseek 后 400,即使 model 已正确改写。

**根因(实测三层)**:
1. 客户端把上一家(MiniMax)的 `reasoning` 项(含 `encrypted_content`)原样回带,DeepSeek 拒收
2. DeepSeek 校验:**带工具往返(function_call/output)+ thinking 模式 → 必须回带 reasoning_text,否则 400**
3. 只剥离推理块还不够——剥离后必须显式 `reasoning.effort="none"`(实测:去掉参数反而 400,effort=none 通过)

**修复**:`stripResponsesReasoning` — /responses 透传前剥离 reasoning 项 + message 里的 reasoning_text 块;剥离且带工具往返时注入 `effort:"none"`。

**预防**:跨厂商续接必然有「状态回带」问题;同一类坑在 anthropic 面(thinking 签名)也潜伏着——Claude Code 默认不回带所以未触发。

## 6. DeepSeek /responses 只支持 deepseek-v4-flash

**现象**:白名单含 `deepseek-v4-pro` 时 Codex 走 deepseek 失败。

**根因**:上游约束(官方文档):`/v1/responses` 目前只支持 v4-flash。

**预防**:Codex 场景白名单放 v4-flash;接新厂商的 Responses API 前先查官方支持矩阵。

## 7. 前端页面全空白(Vue 渲染期异常打崩整个应用)

**现象**:从路由规则页切到其他页面后**所有页面**空白。

**根因**:`/routing` 端点对空 catch_all 返回 `"Providers":null`(Go `append(nil)` 保持 nil),模板里 `data.catch_all.Providers.length` → `null.length` TypeError → 渲染期异常打崩应用。

**修复**:后端 `append([]ProviderRoute{})` 保证返回 `[]`;前端模板 `?? []` 容错。

**预防**:Go API 序列化时**空切片要初始化**,别让前端收到 null;模板对嵌套属性一律容错。

## 8. 页面 500 / 加载失败(进程没在跑)

**现象**:网页报「加载失败: Request failed with status code 500」。

**根因**:gateway 进程没在跑(vite proxy 转发被拒 → 500);常见于后台启动的进程随 shell 退出而死。

**修复**:`nohup ./bin/gateway >> logs/gateway.log 2>&1 &`(从仓库根目录,读 config.yaml;日志追加模式,按天轮转,7 天自动清理)。

**预防**:进程管理(nohup/systemd);vite dev server 同理,重启机器后要手动起。日常更新(加厂商包 / 改 provider 代码)直接 `./gateway-reload.sh`:自动编译 → SIGTERM 优雅排空 → 新进程接管,不用手动 kill+起。重载时 key 状态从 `key-state.json` 快照恢复(QUOTA_EXCEEDED/COOLING/余额不丢,不等 quotacheck 重新 poll);排空窗口(shutdown_timeout,默认 30s)内未结束的长流会被掐断。

## 9. catch_all 空规则被 viper 解成 nil

**现象**:`catch_all: {}` 配置后 `/routing` 显示 null(自动模式没生效)。

**根因**:viper 对空 map + `*AliasRule` 指针不解分配 → nil。「配了空规则」和「没配」是两个语义。

**修复**:`config.Load` 里 `v.IsSet("routing.catch_all")` 后补空 `&AliasRule{}`。

**预防**:三种状态的配置(未配/空/显式)要显式区分,别依赖 mapstructure 的默认行为。

## 10. 真实模型名绕过 tier 链直连声明它的 provider

**现象**:客户端发 `qwen-plus`(真实名,qwen 没 key)→ 502,明明 minimax 有 key 可用。

**根因**:自动发现路径对真实名直连声明者,只有未知名字才走 catch_all。

**修复**:配了 catch_all 后,**所有非 alias 请求一律走链**,模型名只是标签。

**预防**:路由决策只分「协议面 + tier」,名字不参与。

## 11. 同 vendor 双注册名重复统计

**现象**:dashboard 出现两个 deepseek 两个 minimax,QuotaKnownSum 翻倍。

**根因**:`Pools` map 按注册名建 key,同 vendor 共享同一 pool 指针;`poolStatuses` 无脑遍历 → 同一池输出两次。

**修复**:按 `*keypool.Pool` 指针去重(与 quotacheck 的 seen 去重同一不变量)。

**预防**:凡是「多个 key 指向同一对象」的 map,聚合时先按指针去重。

## 12. Gateway Key 绑定 provider 按注册名精确匹配

**现象**:key 绑 `deepseek` 后,anthropic 协议面路由到 `deepseek-anthropic` → 403 key_provider_mismatch。

**根因**:`CheckProvider` 精确字符串比较,而路由产生注册名(协议面)。

**修复**:双侧 `VendorFor` 归一(绑厂商名,两个协议面都放行;旧数据绑注册名也兼容,无需迁移);创建/更新时存储归一为厂商名。

**预防**:任何「绑定时限 + 路由产生不同粒度名字」的系统,比较必须归一化。

## 13. 前端 vite dev server 端口冲突/重复

**现象**:`npm run dev` 报 port in use,起在 5181 而非 5173/5180。

**根因**:已有一个 vite 在 5180(之前启动的)。

**预防**:先 `pgrep -af vite` 看现有实例;页面地址以实际监听端口为准。

## 14. MiniMax anthropic 面套餐耗尽报 HTTP 429(不是 200+base_resp)

**现象**:minimax 某个 token plan key 额度耗尽后,该 key 变成 COOLING 且长时间不恢复(Retry-After 长),另一个健康的 key 也被拖累;整链掉到 deepseek,access log 里却看不到任何 429(failover 掩盖)。

**根因(实测 2026-08-05,直连上游)**:
1. MiniMax **anthropic 面**把套餐耗尽(2056)报成 `HTTP 429 + {"error":{"type":"rate_limit_error","message":"已达到 Token Plan 用量上限... (2056)"}}`,**不是** openai 面的 200+base_resp 格式
2. `looksLikeQuotaError` 关键词表缺「用量/Token Plan/超套餐」→ 429 被分类成 `rate_limit` → key 标 **COOLING**(60s 或 Retry-After)而非 QUOTA_EXCEEDED → 无 poll 恢复路径
3. 每次请求 round-robin 命中该 key → 429 → failover 到健康 key → access log 只记最终成功 → 429 全部隐形,排查时以为"没报错"

**修复**:`looksLikeQuotaError` 增加 `"token plan" / "用量上限" / "超套餐"` 关键词(带回归测试 `classify_test.go`)。现在 429+2056 → quota_exceeded → key 标 QUOTA_EXCEEDED → poll 在 5h 窗口重置后自动恢复。

**预防**:新厂商接入时**直连上游打一次耗尽场景**,记录真实 HTTP status + body(不要只信文档的示例格式);排查"key 异常但 access log 干净"时,先看 key 的 status 是不是 COOLING/QUOTA_EXCEEDED。

## 15. 429 冷却标错 key(双 acquire:路由层和 Provider 层各拿一把 key)

**现象**:某把 key 被反复标 COOLING 但日志里它从没发过请求;真正的 429 发在另一把 key 上;多把 key 同时"坏了",全链掉到 deepseek,access log 里看不到失败(failover 掩盖)。

**根因(实测 2026-08-06,TEMP-DEBUG 日志)**:`RouteIterator.Next()` 拿了一把 key,`Provider.SendRequest` 内部又 acquire 了一把 —— 同一请求两把 key,429 上报时用的是 proxy 的 key(第二把),冷却标到**没发过请求的 healthy key** 上;每次请求都可能冷却两把 key,池子永不恢复。

**修复**:`provider.Request` 增加 `Key *keypool.Key`,路由层已 acquire 的 key 透传给 Provider 层发请求,不再内部二次 acquire(三个基座 anthropic_compatible / openai_compatible / google 统一改)。

**预防**:凡是「上层已选定资源、下层又要自选」的两层设计,下层必须复用上层选择;改 provider 代码时留意 `req.Key == nil` 才走内部 acquire 的兜底分支。

## 16. 熔断器从 provider 级改成 per-key 级(防止连坐)

**现象**:provider 级熔断 OPEN 后整家厂商全部流量被拦,且无恢复路径(历史上 `Allow()` 没被调用,OPEN 就死锁);一把 key 的故障连累同厂商其他健康 key。

**修复(2026-08-06)**:熔断器挂到 keypool,`filterBreakers()` 按 key 过滤;5xx/timeout/connection 触发 `RecordFailure`,只熔断出问题的这一把 key;429/quota/auth/invalid_request 不计入熔断。转移日志记录 CLOSED→OPEN→HALF_OPEN 全程。

**预防**:熔断粒度跟着「故障单元」走 —— key 才是故障单元,provider 不是;接入新厂商时若需熔断,配 provider 块的 `circuit_breaker` 字段(failure_threshold > 0 才启用)。

## 17. 详情页 token 用量行有的请求有、有的没有

**现象**:access log 详情页底部「输入 N · 输出 N · 缓存读 N · 缓存写 N」只有部分请求显示。

**根因**:该行是前端对**响应 body 文本**做 `JSON.parse` 后读 `usage` 字段:非流式请求 body 是完整 JSON ✓ 显示;流式请求 body 是 SSE 拼接文本(`event: ...\ndata: ...`),整体 parse 失败 → 什么都不显示(响应文本也不显示)。用量数据其实在流里(`message_start`/`message_delta` 事件),只是前端没解析。

**现状(有意不修)**:流式请求的 token 数去用量页看 —— 那是内存解析的 usage_records 落库,不受影响。若未来要修:前端逐行拆 `data:` 或后端 detail 接口顺带提取 usage。

**预防**:排查 token 数时以用量页为准,别在详情页找流式请求的数。

## 18. 网络类错误不降档(额度未耗尽绝不落 api 层)

token_plan 层额度未耗尽时,connection/timeout/5xx 类错误在层内解决
(换 key → 换同层 provider),全层穷尽 = 请求失败返回,**不降档到 api 付费层**;
只有额度类证据(quota_exceeded / 429 / **主动 CheckQuota 查询确认 has=false**)
才降档。误判信号:看到 failover 日志里 token_plan provider 网络失败后直接出现
api provider——先查是不是新代码没生效,再查该层是否真有额度证据(换 key 后
二次尝试返回额度类错误的证据同样计入,不要只看首次错误)。

## 19. 控制台 cookie 鉴权的余额端点(未文档化,1 天过期)

部分厂商(MiMo)无官方余额 API,但控制台有未文档化端点(社区逆向,见
cc-switch issue #2488),鉴权是**账号登录 cookie 而非 API key**:
`GET platform.xiaomimimo.com/api/v1/tokenPlan/usage`(套餐)+
`/api/v1/balance`(按量)。关键约束:

- **cookie 是账号级凭据**:所有 key 共享,不能放 key 上;走 config `quota_cookie`
  或管理 API `POST /api/v1/providers/mimo/quota-cookie`(验证 → DB 持久化 → 热注入)
- **约 1 天过期**:过期后 401,轮询跳过、CheckQuota 按未耗尽(保守方向,不误降档);
  日志提示重新上传即可,不用改 config 重启
- **poll 按 vendor pool 去重**:同一 vendor 共享 pool 时随机取一个注册名查 balancer,
  balancer 内必须按 `k.BillingSource` 分支端点(token_plan key → usage 端点,
  api key → balance 端点),不能在注册名上分端点(2026-08-07 设计修正)
- **percent 字段是「已用比例」不是「剩余比例」**:MIMO usage 响应 used=0/limit=11B 时
  percent=0.00(=用了 0%,剩余 100%)。拿 percent>0 判 HasQuota 会把未用的套餐判成
  耗尽(2026-08-07 用户实测:套餐没开用却查询为 0)。剩余% 必须用
  items.plan_total_token 的 (limit-used)/limit 计算;补偿积分
  (compensation_total_token)有剩余也计入 HasQuota(不变式:套餐层未耗尽不落 api)
- 同一 vendor 多注册名共协议(如 mimo openai×2 + anthropic×2)→ 前端协议下拉
  必须去重(`[...new Set(names.map(n => n.protocol))]`),否则出现重复选项

## 20. 候选不适配 ≠ 请求致命;混层共享池的 tier 交集(2026-08-07 三连坑)

Claude Code 请求莫名失败、minimax 却好好的 — 三个问题叠加,排查顺序:

**① 候选顺序随机(catch_all 自动模式)**:`routeCatchAllAuto` 遍历
`manager.GetAll()`(Go map),候选顺序每次请求随机 — 相邻两条相同请求可能一条
先打 mimo、一条先打 minimax。修复:按 name 确定性排序(同 tier 内稳定可解释;
想要自定义顺序配显式 catch_all providers 列表)。

**② 候选不适配被当请求致命**:catch_all 场景客户端模型名只是标签(如
claude-opus-5),body 被重写为候选目标模型(rewriteModelField 已存在,复现
证明生效)。但上游严格校验时仍会拒绝 — MiMo v2.5-pro 不支持图片输入,
Claude Code 历史带截图 → 404 "No endpoints found that support image input";
这类「候选不认标签/不支持输入类型」是**候选不适配**,不是请求坏(minimax
能正常承接)。修复:候选目标模型 ≠ 客户端模型名时,model_not_found /
invalid_request 不再 fatal,继续同层 failover(真实模型直连保持 fatal)。

**③ 混层共享池候选 tier 用并集**:同一 vendor 的 sk-/tp- 两套 key 共享一个
pool 时(mimo),`buildKeyCandidates` 用 `pool.Tiers()`(并集 [token_plan, api])
给每个块生成两层候选 — api 块会拿到 token_plan 候选、把 tp- key 发到 api
端点 → 401 → key 被误标 COOLING。修复:候选 tier = 池 tiers ∩ 块声明
billing_source(交集空 → 回退池并集,兼容旧行为)。

排查线索:access log 里 provider 是「链上第一个候选」不等于「minimax 都失败
了」— 看 P54 DEBUG: trying 的完整序列 + 候选的 error_type(404 image input /
400 Unsupported model 都是候选不适配类)。

1. **access logs 定层**:`GET /api/v1/access-logs?limit=N` — 状态码/error_type/provider/延迟一眼定位是「网关拒绝」「路由无候选」「上游错误」哪一层

## 21. 切库后 key-state.json 快照位置(2026-08-07)

`keyStateSnapshotPath` 的实现是「与 DB 同目录」:SQLite 时在 dsn 的目录
(/tmp/gateway-data/),PG 时 dsn 是 URL → 修后统一落进程 cwd(仓库根)。
systemd 的 `WorkingDirectory=/home/hhhh/llm-gateway` 保证 cwd 稳定且持久。
优雅关停(SIGTERM)时保存、启动时恢复(日志 `key state snapshot saved/restored`)。
注意:快照**不含明文 key**,只含运行时状态(QE/COOLING/余额/熔断),丢了也只
是重启后重新 poll 学习,不致命。

## 22. 删 GORM 结构体字段 = 生产库留雷(2026-08-20 网关全挂实录)

**现象**:重构把模型集迁到 DB 后,网关所有请求 503 `no route`;修完又变成启动崩溃循环。

**根因链**(一个删除动作引发的连锁):

1. `ProviderModel` 重构成 vendor 粒度,从结构体里**删掉** `ProviderName` 字段
2. **AutoMigrate 只加列、不删列** —— 这是它的设计不是 bug(减法可能毁数据,它不敢碰)
3. 于是生产库里 `provider_name` 那一列原封不动留着,还带着 `NOT NULL` 且无默认值
4. 代码不再往这列写值,数据库却要求必填 → **每次 INSERT 必炸**,模型同步全部 500
5. 手工 `ALTER TABLE provider_models DROP COLUMN provider_name` 清掉后,又触发第二跳:
   `Provider` 结构体上的 `Models []ProviderModel gorm:"foreignKey:Vendor;references:Name"`
   关联让 AutoMigrate 改把外键建到 `vendor` 列,而 `providers` 表是空的(全程无人读写)
   → 外键违反 → **AutoMigrate 返回错误 → 启动中止 → systemd 拉起 → 再失败 → 崩溃循环**

**关键认知**:AutoMigrate **不是校验器,是施工队**。它从不报告"库里有列代码不认识",
只会尝试把库改成结构体的样子;改不成就报错中止启动。`provider_name` 在库里躺着的
那段时间,AutoMigrate 一次都没提过它。

**怎么防**(2026-08-20 决定:保持 AutoMigrate 现状,靠纪律补缺口):

- **从 GORM 结构体删字段 / 删关联时,代码改完不算完** —— 必须同时手工对生产库执行
  对应的 `ALTER TABLE ... DROP COLUMN` / `DROP CONSTRAINT`
- 动手前先 `select count(*)` 确认表行数:**空表则零数据丢失,可放心删**
- 跨命名空间不要建外键:`provider_models.vendor` 是厂商名(deepseek/minimax/mimo),
  `providers.name` 是注册面名(deepseek-anthropic / mimo-token-plan…),两者不是同一集合
- 删完立刻重启验证。AutoMigrate 失败是**致命错误、会中止启动**,不会降级运行 ——
  所以漂移一定会以"起不来"的形式暴露,只是暴露得晚

**排查提示**:`ERROR: ... violates not-null constraint` 且列名在 Go 结构体里搜不到,
基本可以断定是这个坑。`\d <表名>` 对照结构体字段,多出来的列就是残留。

**怎么防**:排「no_route 503」时,别只查「key 有没有」,同步查「白名单命中的模型

## 24. route_order 改写序被清 —— 手动排好的路由顺序会「静默退化」到默认序(2026-08-21)

**症状**:前端 Routing 页拖拽排好的顺序(如 token_plan 层 `minimax → mimo`)莫名其妙
丢了,树状图按字典序显示(mimo 跑到 minimax 前面);但后端实际命中有时「看起来还是对的」,
让人误以为没坏。

**根因**:`route_order` 表(Level 2 provider 改写序 + Level 3 key 改写序)是跟着
`sqlite2pg --clean` 那次 TRUNCATE 一起被清空的(不在 specs 清单里,但被 CASCADE 连带)。
表空了 → 启动时 `reloadProviderOrder` 读到 0 行 → `provider order layers = 0` →
路由回退到「最早 key 时间」默认排序。

**为什么「看起来没坏」**:默认序 = 最早 key 时间,而 minimax 的 key(08-05)恰好比
mimo(08-07)早建,所以实际命中还是 minimax 优先——但这是**碰巧**,是建 key 顺序的
巧合,不是你显式排的优先级。一旦哪天重建 key、CreatedAt 重排,顺序就会翻车。

**怎么查**:
- 启动日志 grep `route_order: provider order updated`,看 `layers` 是 2 还是 0(0 = 表空/没加载)
- `/api/v1/routing/order?scope=provider&provider=&billing_source=token_plan` 返回 `order:[]` = 空

**怎么防**:route_order、provider_models、provider_api_keys、gateway_keys、usage_records、
access_logs 这 6 张表都是「会静默退化」的业务状态表,任何 TRUNCATE/清库操作前,
务必先 pg_dump 全量备份,且清完要逐表核对(不只是 key 表)。

**恢复**:从每日 pg_dump 备份提取 route_order 的 COPY 块 INSERT 回去,之后重启网关,
确认 `layers` 回到 2、`/routing/order` 返回正确顺序。

## 25. 中转站厂商「模型按 vendor 合并」→ 部分协议面永远轮不到干活(2026-08-21)

**症状**:接入 API 中转站厂商(rightapi:`/codex/v1`、`/grok/v1`、`/claude-aws` 三个后缀
端点,一把 key 通用)后,该厂商看起来正常 —— `/providers` 三个面都在、模型同步 17 个都在、
请求也有 200。但 access log 里**只有 anthropic 一个面有成功记录**,两个 openai 面 0 条:

```
provider_name | final_model   | status_code | count
rightapi      | claude-opus-5 |         200 |    30    ← 只有 claude 面
```

**根因**:模型归属的维度原本只有 vendor(`provider_models` 按 `(vendor, model_id)` 存一份
合并清单),`ModelsFor` / `DefaultModelFor` 都先 `VendorFor(name)` 归位再查。这条「同 vendor
所有面共享同一份模型清单」的假设对 deepseek/mimo 这类**同一批模型两个协议端点**的厂商成立,
对中转站**不成立** —— 每个后缀是不同上游,模型完全不互通:

```
rightapi 17 个模型合并存一份,sort_order 首行 = claude-haiku-4-5-20251001
→ DefaultModelFor("rightapi-codex") = claude-haiku-4-5-20251001   ← 发给 /codex/v1
→ DefaultModelFor("rightapi-grok")  = claude-haiku-4-5-20251001   ← 发给 /grok/v1
```

实测两个组合都被上游拒:
```
POST /codex/v1/chat/completions {"model":"claude-haiku-4-5-20251001"} → 404 {"error":"model not found"}
POST /grok/v1/chat/completions  {"model":"claude-haiku-4-5-20251001"} → 404 {"error":"model not found"}
```

**为什么没炸成整请求失败**:`proxy.go` 的 `P-catch-all-mismatch` 兜住了 —— 候选模型 ≠ 客户端
模型名且 `model_not_found` → `outcomeContinue` 继续下一个候选。所以表现是「能用」,
代价是**每次白跑一次上游往返**,且那两个面实际是死的。与踩坑 #23 的 mimo openai 面双 `/v1`
同构:面注册了、看着正常、实际静默不可用。

**修法(2026-08-21)**:新增 `provider_model_faces` 表(`(face, model_id)` 唯一),
把归属下沉到**注册面**粒度;`provider_models` 保持不动,继续当定价唯一真相源。

两个设计要点,改之前先想清楚:
- **分支键必须是注册面名,不能是协议** —— 中转站可以有两个同协议、不同 endpoint、模型互斥的面
  (`rightapi-codex` 与 `rightapi-grok` 都是 openai),协议不足以区分。
- **不能给 `provider_models` 加 `face` 列** —— deepseek 双协议面共享同一批模型,加列会产生
  重复行,同一个模型要填两次价格。定价是 `(vendor, model)` 的属性,归属是 `(face, model)` 的
  多对多,拆两张表各自单一职责。`sort_order` 两张表各有一份:顺序是**面内**属性
  (codex 面首个是 gpt-5.4、claude 面首个是 claude-haiku)。

**核心不变式(fallback,别删)**:`ModelsFor` / `DefaultModelFor` 在**该面无归属行**时
退回 vendor 级全量清单。判定粒度是「面」不是「vendor」,两种正当情形都靠它:
- 迁移后尚未同步过的厂商(`provider_model_faces` 空)→ 否则候选全空 → **全部 503**
- anthropic 面这类无模型列表端点的面(`deepseek-anthropic` 的 `ListModels` 返回
  `NotSupported`)→ 它与 openai 面确实共享同一批模型,vendor 全量正是正确答案。
  若按 vendor 判定「有任何归属行就不 fallback」,deepseek 有 openai 面归属 →
  anthropic 面查不到任何模型 → 该面失去全部候选(回归)

守卫测试:`TestModelsFor_FaceIsolation`、`TestModelsFor_FallbackWhenFaceHasNoRows`、
`TestDefaultModelFor_PerFaceOrdering`、`TestSyncVendorModels_FailedFaceKeepsItsAttribution`。

**同步语义**:只有 `ListModels` **成功**的面才 `ReplaceFaceModels`(整体替换);失败 /
`NotSupported` 的面**不动它已有归属** —— 否则上游临时抖动会清空归属,该面掉进 fallback
拿到全厂商模型,等于把本坑重新引入。

**换 channel 后的残留**:`UpsertModels` 只增不删,所以从 `/claude` 换到 `/claude-aws` 后,
官渠独有的 `claude-fable-5` 会留在 `provider_models` 里(不在任何面的归属里 = 无归属)。
模型管理页每个厂商卡片有「清理无归属」按钮(`POST /api/v1/providers/models/prune`),
会连带删掉这些模型的手工价格(它们已无法路由)。
**该 vendor 一条归属行都没有时 prune 整体跳过** —— 否则 `NOT IN (空集)` 会把该厂商模型
全删光(守卫:`TestProviderModelStore_PruneSkipsVendorWithoutFaces`)。

**怎么自查新接的中转站厂商**:
```sql
-- 每个面应各有自己的模型数与首行模型,不该三个面首行都一样
select vendor, face, count(*), min(model_id) filter (where sort_order=0) as first_model
from provider_model_faces group by vendor, face order by vendor, face;

-- 每个面都该有成功记录;某面 0 条 = 它在静默失败
select provider_name, final_model, status_code, count(*) from access_logs
where provider_name = '<vendor>' group by 1,2,3;
```
注意 access log 的 `provider_name` 记的是 **vendor**(`proxy.go` 里 `VendorFor` 归一过),
所以要靠 `final_model` 反推是哪个面在干活。验证某个具体面能否工作,最省事的办法是建一把
只白名单该面模型的 gateway key(如 `allowed_models:["grok-4.5","grok-4.6"]`),
白名单选择会强制路由到那个面。

## 26. 中转站创建/编辑后热重载 panic —— Registry 不允许重复注册(2026-08-24)

**症状**:前端创建/编辑中转站后,请求返回 **500 Internal Server Error**,后端日志
`panic: provider factory already registered: <name>`,进程崩溃或请求失败。

**根因**:中转站创建/编辑触发 `reloadRelayStations` 热重载,逐个调用
`RegisterWithProtocolVendorRelay` 重新注册。但 Registry 的设计假设是「内置厂商
启动时注册一次,不可变」,**不允许同名重复注册**(检测到重复直接 panic)。
这个假设对内置厂商成立(代码静态,不会动态增删),对中转站**不成立** —— 
用户随时可以创建/编辑/删除中转站,需要动态重新注册。

**修复(2026-08-24)**:修改 `provider/registry.go` 的 `RegisterWithProtocolVendorRelay`,
增加 `isRelay` 参数判断:
- 内置厂商(`isRelay=false`):保持原行为,重复注册直接 panic(防止代码错误)
- 中转站(`isRelay=true`):允许重新注册,覆盖旧的 factory(支持编辑场景)

```go
// P-relay-independent: 中转站允许重新注册(支持动态编辑),内置厂商不允许(防止代码错误)
if existing, exists := r.factories[name]; exists {
    if !isRelay {
        panic(fmt.Sprintf("provider factory already registered: %s", name))
    }
    // 中转站:覆盖旧的注册
    log.Printf("INFO: Re-registering relay station: %s (overwriting previous registration)", name)
}
```

**预防**:动态注册的资源(中转站、用户配置的 provider)必须支持「重新注册覆盖」;
静态资源(内置厂商)才应该禁止重复注册。设计 Registry 时要区分这两类场景。

**症状**:创建中转站时 Base URL 填 `https://tokenmarket.cheap/v1`(末尾已包含 `/v1`),
同步模型失败,日志显示 `404: Invalid URL (GET /v1/v1/models)`。

**根因**:协议实现中硬编码了完整路径:
- OpenAI 协议:`ModelsPath = "/v1/models"`
- Anthropic 协议:`modelsPath = "/v1/models"`

拼接时简单做 `endpoint + modelsPath`,导致:
```
https://tokenmarket.cheap/v1  +  /v1/models
→ https://tokenmarket.cheap/v1/v1/models  (错误,双重 /v1)
```

这是中转站常见配置 —— 很多中转站的 Base URL 已包含协议版本前缀(`/v1`),
拼接时需要智能去重。

**修复(2026-08-24)**:

**① OpenAI 协议**(`openai_compatible.go` 的 `ListModels`):
```go
endpoint := strings.TrimRight(b.cfg.Endpoint, "/")
modelsPath := b.cfg.ModelsPath

// P-relay-independent: 防止双重路径 — 如果 endpoint 已包含 /v1 且 modelsPath 以 /v1 开头,去掉 modelsPath 的 /v1
if strings.HasSuffix(endpoint, "/v1") && strings.HasPrefix(modelsPath, "/v1/") {
    modelsPath = modelsPath[3:] // 去掉开头的 "/v1",保留 "/models"
}

fullURL := endpoint + modelsPath
```

**② Anthropic 协议**(`anthropic_compatible.go` 的 `tryAnthropicModels`):
```go
endpoint := strings.TrimRight(b.cfg.Endpoint, "/")
modelsPath := "/v1/models"

// P-relay-independent: 防止双重路径
if strings.HasSuffix(endpoint, "/v1") && strings.HasPrefix(modelsPath, "/v1") {
    modelsPath = "/models" // 去掉 /v1,只保留 /models
}

fullURL := endpoint + modelsPath
```

**预防**:协议实现中拼接路径时,要考虑 Base URL 可能已包含协议前缀的场景。
中转站的 Base URL 格式多样(`https://api.example.com` vs `https://api.example.com/v1`),
拼接逻辑需要智能去重,而不是假设 Base URL 一定不含前缀。

**调试技巧**:ListModels 失败时,添加 DEBUG 日志输出完整 URL,可以立即发现双重路径问题:
```go
fmt.Printf("DEBUG: ListModels for %s: Endpoint=%q, ModelsPath=%q, FullURL=%q\n",

```

## 28. 中转站模型同步的全量替换 vs 增量更新语义(2026-08-24)

**症状**:中转站 API key 在后台配置中切换分组(从 Claude 分组切到 GPT 分组)后,
同步模型时发现数据库中**既有 Claude 模型也有 GPT 模型**,而不是只保留当前返回的 GPT 模型。

**场景理解偏差**:

**初始误解**:以为中转站需要「增量累积」—— 同一个 API key 可以分配多个分组
(GPT 分组 + Claude 分组),每次调用返回不同模型,多次同步应该把所有分组的模型都累积保留。

**实际需求**:中转站的 API key **通过后台配置切换分组**,切换后接口返回的模型会完全不同。
同步应该是**全量替换** —— 删除旧模型,只保留当前接口返回的模型。

**修复尝试与回退**:

① 先实现了增量更新(`AddFaceModels` 方法):
```go
// AddFaceModels 增量添加某面的模型归属(只添加新模型,不删除已有模型)
func (s *gormProviderModelStore) AddFaceModels(ctx context.Context, vendor, face string, modelIDs []string) error {
    // 查询已有模型,只添加新模型,跳过已存在的
    ...
}
```

② 发现不符合需求,回退到全量替换:
```go
// 记下该面自己的归属(整体替换 → 上游下架的模型从该面消失)
if err := store.ReplaceFaceModels(ctx, vendor, n, ids); err != nil {
    return nil, err
}
```

**最终语义**:
- **面级别(Face-level)全量替换**:`ReplaceFaceModels` 删除该面的所有旧归属,插入新归属
- **厂商级别(Vendor-level)累积**:`provider_models` 表中的模型记录累积保留(可能有手工定价)
- **归属关系决定路由**:只有在 `provider_model_faces` 中有归属的模型才能被路由到

**为什么这样设计合理**:
- 切换分组后,旧分组的模型归属被删除,路由时看不到,不会误发到错误的端点
- 模型定价数据保留(可能手工配置过),不会因为切换分组而丢失
- 手动清理按钮(`PruneOrphanModels`)可以删除「在任何面都无归属」的模型记录

**预防**:理解业务场景的实际语义很重要。「同一 key 不同分组」有两种情况:
- **并行多分组**(少见):需要增量累积
- **串行切换分组**(常见):需要全量替换

先确认用户的实际使用方式,再决定同步策略。

## 29. 中转站直通模式的绑定语义 —— Gateway Key 混合绑定时中转站按普通路由走(2026-08-25)

### 现象

- Gateway Key 绑定了 `providers: ["tokenmarket", "deepseek"]`(中转站 + 普通厂商)
- 客户端发送 `gpt-4o` 请求,期望直接透传给 tokenmarket
- 实际:tokenmarket 返回 404 model not found
- 排查:`access_logs` 看到发给 tokenmarket 的模型名不是 `gpt-4o`,而是 tokenmarket 的 default_model

### 根因

**中转站直通模式的触发条件**:Gateway Key 绑定的 **所有** Provider 都是中转站。

判定逻辑(两个维度,任一满足):
1. `GatewayKey.Providers` 字段绑定的所有 provider 都是中转站
2. `GatewayKey.ProviderKeyIDs` 反查出的所有 provider 都是中转站

当 Gateway Key **混合绑定**(既有中转站又有普通厂商)时:
- 路由器走普通路由逻辑
- 中转站也使用 `default_model`(从 DB `provider_models` 取首行模型)
- 客户端请求的模型名被替换,而不是直接透传

### 为什么这么设计

**中转站直通模式** = 成本无优化,纯透传代理:
- 客户端发什么模型名,就发什么给上游
- 不走白名单选择,不走 failover,不走多厂商路由
- **适用场景**:Gateway 只是加一层鉴权/日志,不做任何智能路由

**普通路由模式**(包括混合绑定):
- Gateway 承担"成本优化"角色:按 tier / sticky / failover 智能选择 provider
- 中转站作为候选之一参与路由,和 deepseek / minimax 地位相同
- 使用 default_model 保证候选模型名有效(中转站可能不认客户端的占位模型名)

**混合绑定** = 用户明确要做成本优化(否则只绑中转站就行),因此按普通路由走。

### 解决方案

#### 方案 A:拆分 Gateway Key(推荐)

- **纯中转站 Key**:只绑 tokenmarket → 触发直通模式,透传模型名
- **成本优化 Key**:绑 tokenmarket + deepseek + minimax → 普通路由,failover

```bash
# 纯中转站 Key(透传)
curl -X POST http://localhost:8080/api/v1/keys \
  -H "Content-Type: application/json" \
  -d '{
    "name": "tokenmarket-passthrough",
    "providers": ["tokenmarket"],
    "allowed_models": ["*"]
  }'

# 成本优化 Key(智能路由)
curl -X POST http://localhost:8080/api/v1/keys \
  -H "Content-Type: application/json" \
  -d '{
    "name": "cost-optimized",
    "providers": ["tokenmarket", "deepseek", "minimax"],
    "allowed_models": ["gpt-4o", "claude-opus-5", "deepseek-v4-pro"]
  }'
```

#### 方案 B:前端路由(客户端决策)

- Codex 用 `sk-tokenmarket-xxx`(纯中转站 Key) → 直通
- Claude Code 用 `sk-cost-optimized-xxx`(混合 Key) → 智能路由 + failover

### 实现细节

判定逻辑在 `proxy/relay.go:isRelayPassthrough()`:

```go
func (e *Engine) isRelayPassthrough(gk *auth.GatewayKey) bool {
    if gk == nil {
        return false
    }
    mgr := e.router.Manager()

    // 维度 1: Providers 字段绑定
    if len(gk.Providers) > 0 {
        allRelay := true
        for _, name := range gk.Providers {
            if !mgr.IsRelay(name) {
                allRelay = false
                break
            }
        }
        if allRelay { return true }
    }

    // 维度 2: ProviderKeyIDs 反查
    if len(gk.ProviderKeyIDs) > 0 {
        boundProviders := e.getBoundProviders(gk.ProviderKeyIDs)
        if e.allAreRelays(boundProviders) { return true }
    }

    // 都没绑定 = 不限制 = 不是中转站模式
    return false
}
```

路由层(`router/router.go`)在 catch_all 自动模式下检查 `IsRelayPassthrough`,
若为 true 则直接用 `req.Model` 作为候选,跳过 default_model 和白名单选择。

Proxy 层(`proxy/proxy.go:tryCandidate`)在白名单校验前检查 `IsRelay(provider)`,
若为 true 则跳过白名单逻辑(goto afterWhitelist)。

## 30. Provider 绑定过滤下沉到路由层 —— 探针拿到不允许的 provider(2026-08-25)

### 现象

- Gateway Key 绑定 `providers: ["deepseek"]`
- 客户端发请求,access_logs 里看到 **minimax / mimo 也被尝试过**(status=403)
- 最终返回正确(403 被跳过,deepseek 成功),但:
  - Inflight 页闪现不该出现的 provider
  - metrics 里 `gateway_requests_total{provider="minimax"}` 有计数
  - 上游 minimax 的 key 被无谓 acquire → sticky 指针被推进

### 根因

**修复前**:Provider 绑定过滤只在 `proxy.tryCandidate` 做(白名单校验阶段):

```
路由层 routeCatchAllAuto  → 收集所有 provider 候选(不看 gk.Providers)
       ↓
proxy.tryCandidate        → 逐候选校验白名单 → 不符的返 403 跳过
```

问题:路由层已经为每个候选 **acquire 了 key**(`filterCandidates` → `pool.Acquire`),
即使 proxy 层随后跳过它。副作用:
- sticky 调度器指针被推进(下次请求从下一把 key 开始)
- metrics 计数被污染
- Inflight 快照出现不该有的 provider

### 修复(P19)

Provider 绑定过滤 **下沉到路由层**,在收集候选时就过滤:

```go
// router/router.go — routeCatchAllAuto
for name, p := range r.manager.GetAll() {
    // P19: Provider 绑定过滤 — Gateway Key 限制了 Provider 列表
    if len(o.AllowedProviders) > 0 && !sliceContains(o.AllowedProviders, name) {
        continue
    }
    // ... 协议匹配 / Responses API 检查 / 模型选择
}
```

传递路径(显式参数,不用 magic key):

```go
// proxy/proxy.go — handle
if gk := e.gkCtx.Get(c); gk != nil {
    if len(gk.Providers) > 0 {
        routeOpts = append(routeOpts, router.WithAllowedProviders(gk.Providers))
    }
}
```

### 为什么在路由层而不是 proxy 层

| 维度 | 路由层过滤(P19,现在) | proxy 层过滤(修复前) |
|---|---|---|
| key acquire | 不允许的 provider **不 acquire** | 先 acquire 再跳过 → sticky 被推进 |
| metrics | 干净(只记实际尝试的) | 污染(记了被跳过的) |
| Inflight | 干净 | 闪现不该有的 provider |
| 语义 | Provider 绑定 = **路由候选范围** | Provider 绑定 = 事后否决 |

**核心原则**:能在候选收集阶段排除的,不要留到执行阶段否决。
与 CLAUDE.md 第一要素一致 —— 过滤逻辑归属路由层(职责内聚),
proxy 层只管发请求 + failover(不兼任准入判定)。

### 注意:白名单(AllowedModels)仍在 proxy 层逐候选校验

Provider 绑定和模型白名单的过滤位置**不同**,这是有意设计:

| 字段 | 过滤位置 | 原因 |
|---|---|---|
| `Providers` | 路由层(候选收集时) | 静态集合,provider 名直接可判 |
| `AllowedModels` | proxy 层(逐候选) | 需要 `req.Model` vs `result.ModelID` 双路 fallback(踩坑 #3) |

白名单必须逐候选校验,因为「客户端原始模型名」和「路由选中的候选模型」可能不同,
需要两个都试(见 `tryCandidate` 的 checkModel fallback 逻辑)。

### 验证

```bash

  -H "Content-Type: application/json" \
  -d '{"name":"only-deepseek","providers":["deepseek"],"allowed_models":["*"]}'

# 发请求,确认 access_logs 里只有 deepseek(没有 403 跳过记录)

```

## 31. HTTP 200 之后流里发错误事件 —— 记成 ok、不冷却、不切 key(2026-08-26)

### 现象

用户报:Gateway Key `wyz` 用 `gpt-5.6-sol`,客户端侧收到

```
stream disconnected before completion: Concurrency limit exceeded for account, please retry later
```

而 access log 里这条记录**是成功的**:`status_code=200`、`error_type=ok`、`is_stream=t`。
特征三连:

| 字段 | 值 | 说明 |
|---|---|---|
| `status_code` | 200 | 上游确实回了 200 |
| `error_type` | `ok` | ← 关键错误,网关认为成功 |
| `resp_body_size` | 262 | 正常回答 9KB 量级,262 字节明显不对 |
| `latency_ms` | 31598 / 31927 / 32016 | 上游挂住 ~32s 才失败 |

因为记成 ok,所以:key 不冷却、熔断器不计数、**不 failover 到其他 key** ——
同一把 key 反复被选中,用户侧持续失败。

### 根因

上游先提交 `200 OK` + `Content-Type: text/event-stream`,**然后**在流里发一个
错误事件就收流。整条响应体只有这一个事件(生产实抓,262 字节):

```
data: {"type":"response.failed","response":{"id":"resp_...","model":"gpt-5.6-sol",
       "status":"failed","error":{"code":"rate_limit_exceeded",
       "message":"Concurrency limit exceeded for account, please retry later"}}}
```

网关的失败判定**只看状态码**(`ClassifyErrorWithBody`)。状态码是 200,所以:

```
doStream:
  reportKeySuccess()          ← 此后不可 failover(注释原话)
  w.WriteHeader(200)          ← 状态码锁死
  for chunk := range chunks {
      if chunk.Err != nil { ... }   ← 只看传输错误
      // 从不看 chunk.Data 的内容
  }
```

`chunk.Err` 永远是 nil(传输层没坏,是上游主动说自己失败了),
`chunk.Data` 从没被检查过 → 完美的成功流。

### 修复(P-sse-stream-error,三层)

**沿用已有范式**,不新造机制。两个协议 Base 早就在 `ReportSuccess` **之前**
peek 了流头 2 行跑 `ParseMiniMaxStreamBaseResp`(minimax 的 base_resp 也是
"200 但 body 是错误")—— 在同一个位置加上 SSE 错误事件判定即可。
此时客户端**一个字节都没收到**,failover 仍然可行。

| 层 | 位置 | 行为 |
|---|---|---|
| 1 | `openai_compatible.Base.SendStreamRequest` | peek 命中 → 关 body、`ReportError`、返 `*ProviderError` → **failover** |
| 2 | `anthropic_compatible.Base.SendStreamRequest` | 同上(对称) |
| 3 | `proxy.doStream` chunk 循环 | peek 窗口**之外**的中途错误 → 只标 `error_type`,不动 key 状态 |

覆盖面:全部 12 个 `SendStreamRequest` 实现要么就是这两个 Base,
要么委托它们(中转站 `RelayOpenAIProvider` 内嵌 `*openai_compatible.Base`
且未覆写 → `tokenmarket-codex` 自动覆盖)。

### 关键决策 1:为什么**不**映射到 `ErrorTypeRateLimit`

上游 code 明明叫 `rate_limit_exceeded`,语义上就是限流。但映射过去会走
`retrySameKeyRateLimit` —— **同一把 key、无延迟、重试 10 次**。

该策略假设"429 很便宜(上游立刻拒)"。而这里上游**挂住 ~32s 才失败**
(实测 31.5 / 31.9 / 32.0s),10 次 ≈ **320 秒**,比不识别还难受。

→ 用 `ErrorTypeServerError`,落 `isNetworkClass` → 立刻 `swapToOtherKey`
+ 喂 per-key 熔断(5 次 → OPEN 60s → HALF_OPEN 自动恢复)。

守卫测试 `TestClassifySSEStreamError_NotRateLimit` 锁死这个决策,
防有人"顺手改成语义更像的" 把 32s×10 的坑挖回来。

### 关键决策 2:流**中途**的错误不冷却 key

第 3 层(proxy 中途兜底)刻意**只标 error_type、不动 key 状态**:

- 流已经正常开跑(Provider 早就 `ReportSuccess` 过了)
- 实测中途错误是**内容级**的(minimax 在第 42 个事件发 `output new_sensitive (1027)`),
  这是内容问题不是 key 问题,冷却它是误杀
- HTTP 头已发出、状态码锁死 200,failover 来不及 —— 但 access log 不能记成 ok

### 关键决策 3:判定认**结构**不认关键词

只匹配顶层/`response` 内层的 `error` **对象**,或 `response.status=="failed"`。
正文里出现 "error" 字样的正常回答必须放过 —— 那是字符串值不是顶层键。
否则会把好流打成失败并冷却 healthy key。

### 坑中坑:预筛的超集不变式

热路径每个 chunk 都要过,不能无条件 JSON 解析 → 先做廉价字节预筛
`MayContainSSEError`。**首版只查 `"error"`,漏掉了只给 `status=failed`
的形状** —— 预筛返回 false 就等于宣布"这段不可能有错误",解析器再没机会看。

> ⚠ 不变式:预筛必须是解析器能命中集合的**超集**。

守卫测试 `TestMayContainSSEError_IsSupersetOfParser` 反向从解析器的正样本
校验(不手抄第二份清单),加新错误形状忘了同步预筛就会红。
预筛与解析器同住 `provider` 包,proxy 不自己拼关键词。

### error_type 新值要同步三处(与 CLAUDE.md 十六轮的 status 白名单同源)

新增 `upstream_stream_error` 必须同时改:

| # | 位置 | 漏了会怎样 |
|---|---|---|
| 1 | 写入方(`proxy.doStream`) | 值根本不产生 |
| 2 | `handler/admin.go` 的 `validStatusTokens` 白名单 | 前端一筛就 400 |
| 3 | `frontend/src/views/AccessLogs.vue` 过滤选项 | UI 里筛不到 |

验证白名单真的通了(不是靠读代码):

```bash
curl -s -o /dev/null -w '%{http_code}\n' 'http://127.0.0.1:8080/api/v1/access-logs?status=upstream_stream_error'  # 200
curl -s -o /dev/null -w '%{http_code}\n' 'http://127.0.0.1:8080/api/v1/access-logs?status=bogus_nonsense'          # 400
```

拿真实 body 文件跑真正的 Go 分类器,不是拿构造样本自证:

| 流头窗口命中 | 16 条(全部是真错误) |

### 负向验证(两个都必须红在准确的断言上)

只看测试绿不算验证,得确认它**在没有修复时会红**:

### 线上验证的局限(诚实记录)

部署后发 3 条真实请求,全部 200 / 9KB 正常回答。首事件显示
`"limit_reached":false`、`used_percent: 53` —— 上游当时**健康**,
没能复现并发限制。所以:

- ✅ 证明了新 peek 不误伤正常流(活流量零误判)
- ❌ **没有**在线上观察到 failover 真的发生

这个故障模式取决于上游账号的实时并发状态,无法按需触发。
正确性证据是「语料回放 + 两个负向验证」,不是线上 failover 实录。

### 怎么自查有没有中招

```sql
-- 200 + ok 但 body 小得可疑的流式请求
SELECT id, created_at, requested_model, provider_name, latency_ms, resp_body_size
FROM access_logs
WHERE is_stream = true AND error_type = 'ok' AND resp_body_size < 1000
```
