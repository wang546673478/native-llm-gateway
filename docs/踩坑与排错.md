# 排错指南

本文按当前代码给出可重复的诊断顺序，不保留一次性事故过程。部署和备份见
[`operations.md`](operations.md)，错误处理与状态机见
[`ARCHITECTURE.md`](ARCHITECTURE.md) 和 [`cross-cutting.md`](cross-cutting.md)。

## 先建立一条完整证据链

不要只看客户端最后一个状态码。一次请求可能经历多个 provider/key，最终响应也可能已经
重写。建议按以下顺序收集：

1. 从响应头 `X-Request-Id` 或错误 body 的 `trace_id` 取得 trace id。
2. 检查 `/healthz` 和 `/readyz`，先排除进程与数据库故障。
3. 在 Access Logs 用 trace id 查询所有尝试，按时间查看 provider、Provider Key、
   `status_code`、`error_type`、requested/final model。
4. 对照应用日志中的 `candidate failed, failover`、key 状态和 circuit transition。
5. 再检查 Provider Keys、Models、Routing 页面，确认启用状态、余额、面归属和顺序。

基础命令：

```bash
curl -i http://127.0.0.1:8080/healthz
curl -i http://127.0.0.1:8080/readyz
journalctl -u llm-gateway --since '10 minutes ago' --no-pager
```

管理员 API 使用 `X-Admin-Token` 或 `session_token` cookie，不接受
`Authorization: Bearer`。代理端点使用 Gateway Key，两类凭证不要混用。

## 快速症状表

| 症状 | 优先检查 |
|---|---|
| 进程起不来 | 配置解析、数据库 DSN、端口占用、enabled provider 的 endpoint/protocol |
| `/healthz` 200、`/readyz` 503 | 数据库网络、密码、连接数和 1 秒 ping 超时 |
| 代理 401 | Gateway Key 是否存在、启用，是否使用 Bearer 或 `x-api-key` |
| 管理 API 401 | 是否登录、session 是否过期，是否误用了 Bearer 而不是 `X-Admin-Token` |
| `no_route` 503 | 请求路径协议、模型清单/面归属、Gateway Key 绑定/白名单、可用 key |
| `all providers failed` 502 | 查看同 trace id 的每次上游尝试和最后分类 |
| 重复请求同一 key | 判断是否为 HTTP 429；首次 429 后会同 key 最多再重试 10 次 |
| 新请求没有从预期第一把 key 开始 | 计费层、`route_order`、key 状态、enabled、创建时间 |
| 上游 200 但客户端断流 | SSE 内嵌错误、stream idle timeout、客户端断开 |
| 中转站创建成功但不出流量 | 协议/主协议、模型同步、Gateway Key 绑定、当前 relay 限制 |
| 配置改了没有生效 | 是否属于热重载范围；查看 `config hot-reload is partial` 日志 |
| Access Logs 页面报错 | `server.access_log.enabled`、body 目录权限、管理员 session |
| Usage token 和 Access Log 不一致 | 流式 token 以 Usage 为准；access body 可能截断或已清理 |

## 启动与数据库

### 配置加载失败

典型错误包含 `parse config`、`validate config`。检查：

- `server.port` 必须在 1..65535。
- `database.driver` 只接受 `sqlite` 或 `postgres`，`dsn` 必填。
- 每个启用的内置 provider 必须有 endpoint，protocol 只接受
  `openai|anthropic|google`。注意：这里能解析 `google` 不代表动态 relay 支持 Google。
- duration 使用 Go 格式，例如 `30s`、`5m`、`168h`。
- `routing.catch_all: {}` 表示启用自动兜底；完全不写的语义不同。

可先从最新的 `config.example.yaml` 或 `config.docker.example.yaml` 复制，再逐块迁移私有配置。

### SQLite 锁或写入延迟

SQLite 是单写者。Access log、Usage、管理 CRUD 和状态更新同时写入时，可能出现 lock/busy、
批写延迟或队列堆积。先降低负载并确认磁盘延迟；生产并发场景迁移到 PostgreSQL。不要通过
无限增大内存 buffer 掩盖数据库写不动。

### PostgreSQL 就绪失败

`/readyz` 只有 1 秒数据库 ping 预算。检查 DSN 密码、主机名、TLS 参数、容器网络和连接池：

```bash
docker compose ps
docker compose logs --tail=100 postgres gateway
psql "$DATABASE_URL" -c 'select 1'
```

Compose 内数据库主机名应为 `postgres`，从宿主机连接通常是 `127.0.0.1` 或单独映射的端口，
二者不能混用。

## 认证问题

### 代理端点 401

代理端点在 `auth.enabled=true` 时接受：

```http
Authorization: Bearer gw-...
```

或：

```http
x-api-key: gw-...
```

确认发送的是 Gateway Key，不是上游 Provider key。RPM、provider/key 绑定和模型白名单会
影响请求；模板中的 `auth.keys` 只是启动补种，不会覆盖数据库同名记录。

当前 Gateway Key 管理有三个容易造成误判的限制：

- `gateway_keys.enabled=false` 只会改变数据库和页面显示，加载与 CRUD 重载仍把该 Key 放入
  Authenticator。需要吊销时删除 Key，并用旧值确认代理端点返回 401。
- TPM 当前只累计成功请求的实际 token，入口没有执行 TPM 拒绝检查；排查限流只把 RPM
  视为已强制生效。
- `default_model` 的 PUT 更新不会持久化，CRUD 内存重载也不复制默认模型。出现默认模型未
  改写时，不要只看页面回显；在修复前应依赖明确 alias/catch-all 和模型白名单。

### 上游 401/403 与网关 403

先用 access log 判断错误发生位置和 `error_type`：

- `auth`：通常是上游 key 无效/权限不足。该 key 固定进入 5 分钟 `COOLING`，随后自动重试。
- `rate_limit` + HTTP 403：不是纯 HTTP 429，不会同 key 循环；立即换 key/候选。
- `quota_exceeded`：进入额度恢复路径；有 balancer 的厂商由 poll 恢复，无 balancer 时按
  probe 策略处理。
- `model_not_allowed` / `key_provider_mismatch`：是 Gateway Key 白名单或绑定，不是上游鉴权。

`keypool.cooling_duration` 只控制普通 rate-limit 冷却，不能修改 auth 的固定 5 分钟。

### 管理后台无法登录

`admin_auth.enabled=true` 时必须显式配置：

```yaml
admin_auth:
  enabled: true
  session_ttl: 168h
  max_login_attempts: 5
  login_ban_duration: 15m
```

当前 Server 直接传递零值，缺字段会产生立即过期 session、首次错误就锁定等异常行为。首次
root 是 `admin / Gateway@2026`；修改后以数据库密码 hash 为准。连续失败达到阈值后，当前
前端“解锁”动作与后端契约不一致，必要时由 root 重置密码或直接审慎修正用户锁定字段。

`admin_auth.enabled=false` 时管理 API 不鉴权，但 SPA 路由仍强制登录，而登录端点返回
`feature_disabled`。因此浏览器管理页当前要求启用管理员认证。

## 路由和 key 调度

### 为什么新请求没有从“第一把 key”开始

默认 `sticky` 不记录上一次成功位置，选择过程是：

1. 先选最高可用计费层：`token_plan -> api -> free`。
2. 在层内按 `route_order` 的 provider 顺序；没有改写时按最早 key 创建时间，再按名称稳定排序。
3. 在 provider 内按 `route_order` 的 key 顺序；没有改写时按 key 创建时间。
4. 过滤 disabled、`COOLING`、`QUOTA_EXCEEDED`、额度耗尽、协议不匹配和 OPEN circuit 的 key。
5. `sticky` 取过滤后列表第一个。

所以“没有从预期第一把开始”通常不是游标，而是预期 key 当时不可用、位于较低计费层、
被 route order 覆盖，或其 provider 没进入候选。高位 key 恢复后会自动回位。

排查时同时看 Routing 保存顺序和 Provider Keys 的 runtime status。数据库 `route_order` 是
持久化改写，重启不会清除。

### 为什么 HTTP 429 看起来重复了很多次

纯 HTTP 429 `rate_limit` 首次失败后，会在同一把 key 上最多再重试 10 次；也就是切换前
同一 key 最多产生 11 次 HTTP 尝试。仍失败后冷却该 key，再尝试同 provider 的其他
key/候选。这是代码固定策略，不由 `retry.max_attempts` 控制。

`retry.max_attempts` 计算的是每个计费层的候选数，不是底层 HTTP 次数。设为 `0` 表示尝试
该层全部候选，因此“候选多 × 每把 key 多次 429”会放大最坏延迟。

非 429 的 `rate_limit` 必须立即退出同 key 重试。如果 access log 显示 403 同一 key 连续
多次，检查运行二进制是否包含当前修复，并用同一 trace id 区分客户端重试与网关内部尝试。

### `no_route` 503

依次检查：

- 请求路径是否选择了正确协议面：`/v1/messages` 是 Anthropic，Chat/Responses 是 OpenAI。
- Gateway Key 是否绑定了允许的 vendor 或具体 Provider Key ID。
- `allowed_models` 是否允许客户端标签或候选真实模型。
- Models 页面是否有 vendor 模型，协议面是否有正确 `provider_model_faces` 归属。
- provider 是否 enabled、已加载且存在当前计费层可用 key。
- Responses 请求只会选择启用 Responses 能力的注册面。

模型同步成功后才会把上游清单写入数据库。Anthropic 面没有独立 `/models` 时可合理回退到
vendor 级清单；多面中转站则必须保持每个 face 的模型归属隔离。

### failover 没有降到下一计费层

层切换不是“任何失败都降档”。`token_plan` 层需要额度类证据才允许降到 `api`；普通 429、
网络错误、auth 或候选不适配不一定构成额度耗尽。先看 `error_type` 是否为
`quota_exceeded`，再看 quota poll/probe 是否能恢复。

## URL 与协议

### 双 `/v1`、漏 `/v1` 或路径重复

动态中转站只保存 base URL，最终资源 URL 由协议实现构建：

- OpenAI：`openai_compatible` 根据 Chat/Responses/Models 路径归一化。
- Anthropic：`anthropic_compatible.buildMessagesURL` 归一化 Messages 路径。
- relay 包不存在单独的 `normalizeEndpoint`。

测试 base URL 时至少覆盖：

```text
https://relay.example.com
https://relay.example.com/
https://relay.example.com/v1
https://relay.example.com/v1/
```

然后分别实测 `/v1/chat/completions`、`/responses`/`/v1/responses`、`/v1/messages` 和模型同步。
不要通过在 relay 层统一删 `/v1` 修复，这会破坏把版本前缀作为上游路径一部分的站点。

## 动态中转站

当前中转站有以下限制，排障时不要按 UI 字段的表面能力推断：

- 只支持 OpenAI 与 Anthropic；前端虽仍可选择 Google，后端加载会拒绝。
- `billing_source` 当前没有贯穿运行时，中转站同步出的 Provider Key 固定为 `api`。
- multi 模式的多个 face 共享一个 `GenericRelayProvider`，其 `Protocol()` 返回主协议；当前路由
  实际不能可靠使用所有声明协议。优先为每个协议创建独立 single 站。
- relay pool 没有从 YAML 读取 circuit 配置，当前没有内置厂商同等的 per-key breaker。
- `keys` 在 `relay_stations` 与 `provider_api_keys` 都以明文保存，管理列表也会返回明文。

创建/编辑后 handler 会自动 reload；另有手工 `POST /api/v1/relay-stations/reload`。如果站点
已创建但不可用，检查：

1. `enabled`、base URL、single 主协议和 timeout。
2. key 长度是否至少 8 个字符；同步代码用末 8 位生成名称，过短值不会进入 Provider Key 表。
3. 模型同步是否成功，face 归属是否属于该站而非同名前缀的另一站。
4. Gateway Key 的 provider/key 绑定是否允许该 relay，face 模型清单是否包含客户端模型。
5. 上游是否真的支持所选请求路径，而不只是宣称“OpenAI 兼容”。

Relay 无论纯绑定还是与内置厂商混合绑定，都透传客户端模型名并跳过 Gateway Key 模型
白名单。混合绑定中的内置厂商候选仍受白名单约束。详情见
[`relay-stations.md`](relay-stations.md)。

删除中转站会清理面归属、route order 和 Provider Key。数据库中的关联是字符串而非完整外键，
旧版本留下的孤儿数据应先备份和只读预览，不要直接运行带固定活面清单的历史 SQL。

## 流式请求

### HTTP 200 后立刻断流

上游可能先返回 200，再在 SSE 中发送 `response.failed`、顶层 `error` 或
`response.status=failed`。兼容基类会在首个客户端字节前识别结构化错误并允许 failover；
这类错误通常记为 `upstream_stream_error` 或对应额度分类，而不是简单的 `ok`。

已经输出正常内容后的中途错误不能换 key 重放，否则客户端会收到重复内容。此时网关只记录
错误并结束流。用 trace id 对照 response body、`error_type` 和应用日志。

### 长流被中止

检查三个不同预算：

- provider `timeout`：上游请求 context。
- 流式 idle timeout：按请求 body 大小硬编码分段；小于 100 KiB、500 KiB、1 MiB、
  2 MiB 时分别为 10、15、20、30 秒，2 MiB 及以上为 45 秒。
- `server.write_timeout`：流式按 chunk 续期，非流式是绝对写上限。

动态 idle timer 在第一个缓冲 chunk 已发送后才启动。`Engine.StreamIdleTimeout` 虽被初始化，
但 `calculateIdleTimeout` 当前不读取它；YAML 也没有对应的可用覆盖项。还要排除反向代理、
客户端和负载均衡器自身的 idle timeout。改变未被运行时消费的 timeout 字段不会影响行为。

## Access Log、Usage 与指标

### `access_log_disabled`

设置 `server.access_log.enabled: true` 并重启。该模块、body 目录和 retention 不属于当前
热重载范围。确认服务用户可创建目录和文件。

metadata 存数据库，request/response body 是每请求一个 JSON 文件；不是 JSONL。JSONL 只在
导出 API 生成。单 body 超过 16 MiB 会截断，retention 清理后详情仍可能有 metadata 而 body
为空。

### 流式 token 显示为 0 或与 body 不一致

Usage collector 从最终协议 usage 事件异步写库；Access Log 详情不是 token 权威来源。先等待
`usage.flush_interval`，再查 Usage 页面。客户端中途断开、上游没发 usage 或流在首帧前失败时，
token 可以合理缺失。

### 指标配置不生效

`/metrics` 当前总是在主服务端口注册，`metrics.enabled/path/port` 只解析不消费。抓取固定访问
`http://gateway:<server.port>/metrics`。指标中的最终 status 不能替代 access-log 尝试链。

## 配置热重载

日志出现 `config reloaded` 只说明部分字段生效。以下通常需要重启：

- database 和 server 监听/timeout/static/access-log
- usage collector batch/flush
- provider 实例、endpoint、protocol、timeout
- admin auth 开关和参数
- fingerprint canonical device id

文件修改后查看紧随其后的 `config hot-reload is partial` 警告。Provider Key、中转站、模型和
route order 应走各自管理 API，不要只改数据库后等待 YAML watcher。

## 前端显示与 API 不一致

先在浏览器 Network 面板确认请求路径、body 和后端响应，再以 handler 契约为准。当前已知问题
集中记录在 [`frontend.md`](frontend.md) 的“已知契约问题”，包括管理员解锁、relay 计费来源、
部分 routing/free-tier 显示等。不要通过修改文档或前端类型掩盖后端实际响应。

构建生产前端后才会更新 `frontend/dist`：

```bash
npm --prefix frontend ci
npm --prefix frontend run build
```

开发服务器默认 5180；生产页面由 gateway 的 `server.static_dir` 托管，不经过 Vite。

## 数据与凭证安全

`provider_api_keys.key_hash`、`gateway_keys.key_hash`、relay `keys` 和管理员 session token 当前
都包含可用明文。`GET /api/v1/keys` 也仍返回 Gateway Key 原值。排错时：

- 不把完整 DB 行、curl header、body 文件或 SQL dump 粘贴到工单/聊天。
- 日志只记录 key ID/名称或末尾少量掩码，不记录原值。
- 暴露后立即在上游吊销并轮换；从文件删除不能使已泄露凭证失效。
- 备份、数据库、access body 和本地 `config.yaml` 使用最小权限并加密保存。

发现仓库中的示例疑似真实凭证时，停止传播该值，清除默认值并通知凭证所有者轮换；是否重写
Git 历史需与所有协作者单独协调。
